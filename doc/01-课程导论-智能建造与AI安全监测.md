# 第 1 篇：为什么智能建造需要 AI 安全监测？——系统全景与三条业务链路

> 系列博客第 1 篇。先带你看清这套系统的全貌：它解决什么问题、由哪些部分组成、三条业务链路分别干什么。

---

## 开头：一个让我印象深刻的现场

做这套系统之前，我去过一个工地。安全员老王跟我抱怨："监控装了 30 多个摄像头，我总不能盯着 30 块屏幕看吧？"他给我看了上个月的记录——3 起高处坠落隐患，全部是事后翻录像才发现的，翻了整整两天。

这就是工地的现状：**摄像头很多，但"眼睛"不够**。

而 AI 视觉恰好能补上这个缺口：让每个摄像头都变成"不眨眼的安全员"，违规瞬间自动抓拍留痕。本系列博客要讲的，就是一套真实落地、可运行的"工地 AI 安全监测系统"。

## 1. 这套系统到底干了什么？

一句话版本：**对接 RTSP 监控摄像头，用 YOLOv8 实时识别违规穿戴，自动抓拍入库，网页后台管理。**

展开来说，它有五层能力：

| 能力层 | 干什么 | 例子 |
|---|---|---|
| AI 识别 | 识别画面里的安全帽/马甲/口罩及违规情况 | 模型直接输出"NO-Hardhat"（没戴安全帽） |
| 视频接入 | 摄像头画面稳定地在浏览器里播放 | MediaMTX 把 RTSP 转成浏览器能播的 FLV |
| 自动留痕 | 违规瞬间截帧，存原始图和标注图 | 每张违规记录都有"证据图" |
| 后台管理 | 看板、记录、日志、报表、预警 | 7/30/90 天趋势、Excel/PDF 导出、铃铛预警 |
| 演示能力 | 不接摄像头也能现场演示 | 笔记本摄像头 + 后端直接推理 |

仓库结构对应关系：

```
yolo-safety-system/
├── backend/        # FastAPI 后端（接口、数据库、演示模式推理）
├── inference/      # 推理服务（正式链路：拉 RTSP 流 + YOLO 检测）
├── frontend/       # Vue3 网页后台
├── deploy/         # MediaMTX 流媒体配置
├── Safety-Detection*.py   # 原始脚本（本地视频检测，独立于系统）
├── weights/        # 模型权重集中目录（ppe/ppe.pt、fire/fire.pt）
└── doc/            # 你正在读的系列博客
```

## 2. 核心概念先扫盲（后面每篇都会用到）

### 2.1 RTSP：摄像头的"母语"

监控摄像头（海康、大华等）原生协议是 RTSP（Real Time Streaming Protocol，TCP 554 端口）。系统里每台摄像头存的就是一个 `rtsp_url`：

```
rtsp://admin:password@192.168.1.64:554/h264/ch1/main/av_stream
```

注意：**浏览器不能直接播 RTSP**（浏览器只支持 HTTP 系协议）。所以需要 MediaMTX 做中转——RTSP 进去，FLV/WebRTC 出来。这是"实时监控页能播放"的底层原因，第 4、7 篇会展开。

### 2.2 ppe.pt：10 类的 PPE 检测模型

ppe = Personal Protective Equipment（个人防护装备）。这个模型输出 **10 个类别**：

```
0 Hardhat(安全帽)    1 Mask(口罩)         2 NO-Hardhat(没戴安全帽)
3 NO-Mask(没戴口罩)  4 NO-Safety Vest(没穿马甲)  5 Person(人)
6 Safety Cone(锥桶)  7 Safety Vest(马甲)  8 machinery(机械)  9 vehicle(车辆)
```

**最关键的设计**：模型直接输出"违规类"（`NO-*` 前缀）。所以违规判定可以用最简单的 `direct` 模式——**出现 NO-Hardhat 就判定"未戴安全帽"**，不需要任何后处理逻辑。

### 2.3 违规类型 key：系统内部的语言

系统内部违规类型用三个 key，前端展示中文：

| key | 中文 | 触发条件（direct 模式） |
|---|---|---|
| `no_helmet` | 未戴安全帽 | 检测到 `NO-Hardhat` |
| `no_vest` | 未穿安全马甲 | 检测到 `NO-Safety Vest` |
| `no_mask` | 未戴口罩 | 检测到 `NO-Mask` |

映射关系定义在 `backend/app/config.py` 的 `VIOLATION_RULE`：

```python
VIOLATION_RULE: dict = {
    "no_helmet": "NO-Hardhat",
    "no_vest": "NO-Safety Vest",
    "no_mask": "NO-Mask",
}
```

> 💡 为什么存 key 不存中文？因为**中文是展示层的职责**。存 `no_helmet`，前端想显示"未戴安全帽"还是"未佩戴安全帽"随时改；存中文的话，改一次要动数据库。这是数据设计的基本准则，第 6 篇会再讲。

## 3. 三条业务链路：为什么是三条？

这是本系列最重要的一张图，请记住它：

### 链路一：正式链路（真实部署）

```
RTSP 摄像头 → MediaMTX 转发 → 推理服务(OpenCV拉流)
  → YOLOv8 检测 → direct 判定 → 自动抓拍
  → POST /api/violations/with-image → 后端入库
  → 前端展示/导出/预警
```

代码路径：`inference/main.py`（入口，拉取启用摄像头列表）→ `inference/stream_worker.py`（每摄像头一个线程，拉流+检测+上报）。

### 链路二：临时演示链路（笔记本摄像头）

```
浏览器 getUserMedia 取帧 → 每 500ms POST /api/demo/detect
  → 后端直接推理（懒加载单例+预热）→ 判定 → 违规入库(camera_id=0)
```

代码路径：`frontend/src/views/demo/index.vue` + `backend/app/routers/demo.py`。

### 链路三：原始脚本（本地视频文件）

```
uv run python Safety-Detection.py            # 实时窗口播放检测
uv run python Safety-Detection-export-gpu.py --input videos/x.mp4 ...  # 导出标注视频
```

独立于系统，共用 `ppe.pt`，只做本地视频的检测与标注导出。

**为什么要设计三条链路？** 这是典型的工程思维：

- 正式链路要**稳**：多线程、断流重连、去重、心跳；
- 演示链路要**快**：零设备依赖，客户现场 5 分钟跑起来；
- 脚本链路要**纯**：不依赖数据库和网络，纯本地调试模型。

**同一条判定逻辑**贯穿三条链路——`inference/` 与 `backend/app/detection/` 的 `detector.py`、`judge.py`、`annotate.py` 是**逐行一致的**（双份同步，第 5 篇详细讲）。

## 5. 快速体验：5 分钟跑起来

```bash
cd backend && uv sync && uv run uvicorn app.main:app --reload   # 终端1
cd frontend && npm install && npm run dev                       # 终端2
```

打开 http://localhost:3000，`admin / admin123` 登录，点「临时演示」，授权摄像头，**对着镜头摘一下口罩**——你会看到红色检测框和"违规"横幅，切到「违规记录」页，刚才的抓拍已经入库了，还有一张标注证据图。

这套"零设备演示"能力的底层：`backend/app/main.py` 启动时后台线程预热模型，`demo.py` 用懒加载单例 + 线程池推理。第 6、7 篇会逐行讲。

## 总结

- 系统解决"摄像头多、眼睛不够"的问题：AI 自动识别 + 抓拍留痕 + 数据管理；
- ppe.pt 直接输出违规类（`NO-*`），判定用最简单的 direct 模式；
- 三条链路（正式/演示/脚本）共享同一套检测判定逻辑（双份同步）；
- 5 分钟就能本地跑起来，笔记本摄像头即可完整体验。
