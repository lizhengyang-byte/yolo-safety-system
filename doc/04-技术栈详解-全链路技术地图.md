# 第 4 篇：这套系统用了哪些技术，为什么是它们？——全链路技术地图

> 系列博客第 4 篇。技术选型是项目的地基。这一篇把本项目用到的 16 项技术逐个讲透，重点不是"它是什么"，而是"**为什么是它、不是别的**"——以及每个技术背后的底层原理。

---

## 开头：选型就是一场"妥协的艺术"

技术选型没有标准答案，只有"**在这个场景下最合适**"的答案。做这套系统时的场景约束是：

- 要做 AI 检测（YOLO）→ 离不开 Python 生态；
- 要实时监控、并发上报 → 后端要异步；
- 要给客户演示、快速部署 → 前端要快、部署要简单；
- 要出报表 → 要有 PDF/Excel 生成能力；
- 要应对"客户现场没 Docker" → 要有零依赖方案。

带着这些约束，逐个看选型。

## 1. Python 3.12：为什么没得选

AI 检测几乎是 Python 的"垄断"领域：Ultralytics（YOLOv8）、OpenCV、numpy、PIL 全是 Python 生态。**选型要围绕瓶颈走**——本系统的瓶颈在"AI 推理计算"，不在"接口吞吐"，所以 Python 足够，C++ 没必要。

**依赖管理用 uv**：一条 `uv sync` 完成虚拟环境 + 依赖安装 + lockfile。仓库里有**三份独立 pyproject.toml**（backend / inference / 根目录脚本），各自管理。

PyTorch 的固定方式很值得注意（`[tool.uv.sources]`）：

```toml
[tool.uv.sources]
torch = { index = "pytorch-cu132" }
```

**底层原理**：PyTorch 有 CPU 版和 CUDA（GPU）版，直接 `pip install torch` 默认装的是 CPU 版。通过 uv 指定 `pytorch-cu132` 索引，有 NVIDIA GPU 时装 CUDA 版，没有则回落 CPU。这样同一份配置文件适配两种机器。

> ⚠️ 坑：`uv sync` 偶尔会因 ultralytics 解析失败（网络/索引问题，与代码无关），单独补装即可，例如 `uv pip install reportlab==4.2.5 --python ../.venv/Scripts/python.exe`。

## 2. FastAPI：为什么不是 Flask 或 Django？

| 框架 | 特点 | 结论 |
|---|---|---|
| Flask | 轻量、灵活，但异步支持弱 | 实时监控/演示要并发，放弃 |
| Django | 全家桶（ORM/Admin/认证），但重 | 不需要 Admin 后台，放弃 |
| **FastAPI** | 原生 async、Pydantic 校验、自动 Swagger 文档、性能接近 Go | ✅ 选它 |

FastAPI 的底层原理要搞清楚三件事：

**① 原生异步（async/await）**：FastAPI 基于 Starlette（asyncio），事件循环单线程处理并发。`demo.py` 里这个写法是关键：

```python
@router.post("/detect")
async def demo_detect(...):
    # 同步推理放进线程池，不阻塞事件循环
    detections = await run_in_threadpool(detector.predict, img, conf or None)
```

**底层原理**：YOLO 推理是 CPU 密集的同步操作，如果直接在 async 函数里跑，会**卡死整个事件循环**——所有并发请求（登录、心跳、列表）全部排队。`run_in_threadpool` 把推理丢给线程池，事件循环立刻腾出来继续处理其他请求，推理完再回来取结果。

**② Pydantic 校验**：`file: UploadFile = File(...)`、`conf: float = Form(None)` —— 请求参数自动校验，类型错了直接 422 返回，业务代码不用写 if。

**③ 免费 Swagger 文档**：启动后访问 http://localhost:8000/docs，所有接口可交互测试。演示、调试、给客户展示接口全靠它。

## 3. SQLAlchemy ORM：一张代码适配两种数据库

**底层原理**：ORM（Object-Relational Mapping）把 Python 类和数据库表映射起来。`models.py` 里定义的 `Camera` 类 → `cameras` 表，`db.query(...)` → SQL 查询。好处是**不用手写 SQL**，且表结构变更集中在一个文件。

最关键的是**双数据库兼容**（`database.py`）：

```python
engine_kwargs = (
    {"connect_args": {"check_same_thread": False}, "echo": False}
    if settings.DATABASE_URL.startswith("sqlite")
    else {"pool_pre_ping": True, "pool_recycle": 3600, "pool_size": 10, "max_overflow": 20}
)
engine = create_engine(settings.DATABASE_URL, **engine_kwargs)
```

**底层原理**：
- **SQLite 需要 `check_same_thread=False`**：SQLite 默认不允许跨线程用同一连接，但 FastAPI 是线程池并发处理请求，必须关掉这个限制；
- **MySQL 需要连接池参数**：`pool_pre_ping`（每次取连接先 ping，防连接被服务端断开）、`pool_recycle`（3600 秒回收）、`pool_size`/`max_overflow`（连接数上限）。SQLite 文件数据库不需要这些。

> ⚠️ **本项目最深的坑**（第 9 篇展开）：SQLite 的 `CURRENT_TIMESTAMP` 返回 UTC 时间，比本地时间（UTC+8）差 8 小时，导致预警统计永远差 8 小时。解法是统一用 Python 侧 `default=datetime.now` 写入。

## 4. Ultralytics YOLOv8：实时目标检测的事实标准

**为什么是 YOLO 而不是其他？**

| 方案 | 问题 |
|---|---|
| 传统 CV（颜色分割/HOG） | 光照、遮挡一变就失效 |
| 两阶段检测（Faster R-CNN） | 精度高但慢，达不到实时 |
| 图像分类（整张图判断） | 不能定位"谁违规、在哪"，无法画框取证 |
| **YOLOv8** | 实时 + 可定位 + 预训练 + API 极简 ✅ |

**YOLOv8 底层原理（重点）**：

YOLO = You Only Look Once，一阶段检测器。核心思想：**把检测当成回归问题，一次前向传播同时预测所有目标的类别和位置框**。

相比 YOLOv5，v8 的几个关键升级（理解这些，答辩时能讲出"内行话"）：

- **Anchor-Free（无锚框）**：不再预设固定尺寸的锚框，而是直接在特征图上预测每个位置到目标中心的距离。好处：少一堆超参数、小目标检测更稳；
- **C2f 模块**：Cross Stage Partial 的升级版，在特征融合中更有效地保留梯度信息，精度/速度平衡更好；
- **Decoupled Head（解耦头）**：分类和回归分支分开预测，不再共享一个检测头——分类任务和定位任务的学习目标不同，分开更准；
- **损失函数**：分类用 BCE，回归用 CIoU，外加 DFL（Distribution Focal Loss）让框更精准。

本项目对 Ultralytics 的封装（`inference/detector.py`）：

```python
class YoloDetector:
    def __init__(self, model_path, conf_threshold=0.5, device="cpu"):
        self.model = YOLO(model_path)
        self.names = self.model.names   # 类别索引 -> 名称

    def predict(self, image, conf=None) -> List[Detection]:
        conf = conf if conf is not None else self.conf_threshold
        results = self.model.predict(source=image, conf=conf, device=self.device, verbose=False)
        # 遍历 box.cls / box.conf / box.xyxy → 组装成统一 Detection 结构
```

两个细节的底层原因：
- **`verbose=False`**：Ultralytics 默认每帧打印检测日志，视频流检测会刷屏；
- **封装成统一 `Detection`**：屏蔽 Ultralytics 的 `Results` 对象差异，下游（判定/标注/上报）只依赖自己的数据结构——**适配层模式**，换检测框架不惊动业务代码。

## 5. OpenCV：拉流、读写、画框全靠它

| 任务 | OpenCV 函数 |
|---|---|
| 拉 RTSP 流 | `cv2.VideoCapture(rtsp_url)` |
| 读帧 | `cap.read()` |
| 图片编解码（接口传输） | `cv2.imencode(".jpg", img)` |
| 保存抓拍 | `cv2.imwrite(path, img)` |
| 画检测框/横幅 | `cv2.rectangle` / `cv2.putText` |

**底层原理**：OpenCV 的图像数据是 numpy 的 `ndarray`，BGR 三通道。YOLO 吃进去、标注画出来、存文件、传接口，全程都在 numpy 世界——这也是 Python 做视觉的优势。

> ⚠️ 注意：OpenCV 用 **BGR** 通道顺序，浏览器 Canvas 用 **RGB**。前端画框颜色（`#f56c6c` 红）和后端画框颜色（`(0,0,255)` 红）要**人工对齐**，这是跨栈配色一致性的坑，第 8 篇展开。

## 6. MediaMTX：解决"浏览器不能播 RTSP"

**底层原理**：监控摄像头的 RTSP 是 TCP 554 端口的长连接协议，浏览器根本不支持。要在网页看监控，必须把 RTSP 转成浏览器能播的格式（FLV / WebRTC / HLS）。

MediaMTX 做的就是这件事（`deploy/mediamtx.yml`）：

```yaml
rtspAddress: :8554     # RTSP 入口
httpAddress: :8080     # HTTP 出口（FLV/WebRTC/HLS）
```

前端用 **flv.js** 播放 `http://localhost:8080/live/{id}.flv`（地址前缀来自 `frontend/.env` 的 `VITE_MEDIAMTX_BASE`）。

**为什么用 MediaMTX 而不直接连摄像头？** 稳定。直接连摄像头 RTSP 容易断流、一拉流就占满带宽；经 MediaMTX 转发后，前端/推理服务从 MediaMTX 拉流，摄像头只推一路给 MediaMTX，稳定性和并发都更好。

## 7. Vue3 + TypeScript：中文中后台的最优解

**为什么是 Vue3 而不是 React？** 对"中后台管理系统"（登录、表格、表单、弹窗、图表）这类需求，Vue3 + Element Plus 是成熟度最高、中文文档最全的组合。React 适合复杂交互应用，但这里用不上。

几个底层要点：

**① `<script setup>` 组合式 API**：组件逻辑按"功能"组织，而不是按"选项"（data/methods）——复用和可读性更好。本项目页面（如 `Dashboard.vue`）都这么写。

**② TypeScript 类型安全**：接口响应有类型（`api/violation.ts` 的 `DashboardData`），字段名写错在**编译期**报错，而不是运行时 undefined。

**③ Vite 构建 + 开发代理**（`vite.config.ts`）：

```typescript
server: {
  proxy: {
    "/api": { target: "http://localhost:8000", changeOrigin: true },
    "/images": { target: "http://localhost:8000", changeOrigin: true },
  },
}
```

**底层原理**：开发时前端在 3000 端口，后端在 8000。浏览器直接访问 `/api/xxx` 会跨域（CORS）。Vite 代理把 `/api` 请求**转发到后端**，前端代码以为在同一个域——零 CORS 问题。生产环境同理，由 nginx 反代（`frontend/nginx.conf`）。

## 8. Element Plus / ECharts / flv.js / axios：各自干一份活

| 技术 | 干什么 | 底层要点 |
|---|---|---|
| Element Plus | 表格/表单/弹窗/消息 | `el-table` 数据绑定、`el-dialog` 弹窗、`ElNotification` 全局消息 |
| ECharts | 看板图表 | **按需引入**（只引用到的图表），打包体积 1.1MB→560KB |
| flv.js | 视频播放 | 浏览器原生不支持 FLV，flv.js 用 MSE（Media Source Extensions）解码播放 |
| axios | HTTP 请求 | 拦截器：请求自动加 token、响应统一错误处理、401 跳登录 |

## 10. Docker Compose：五容器编排

`docker-compose.yml` 编排 5 个容器：

```
mysql（数据库）→ mediamtx（流媒体）→ backend（后端）→ inference（推理服务）→ frontend（前端）
```

关键设计：
- 后端用环境变量覆盖配置：`DATABASE_URL` 指向 MySQL、`UPLOAD_DIR=/data/images`；
- `inference/weights` 挂载给后端（演示模式复用同一份模型权重）；
- 推理服务 GPU 可选（`deploy.resources.reservations.devices`，无 GPU 可移除）；
- 前端 nginx 反代 `/api`、`/images` 到 backend。

## 总结

| 技术 | 一句话记住它 |
|---|---|
| Python + uv | AI 生态没得选；uv 一条命令管理依赖，PyTorch 分 CPU/CUDA 两索引 |
| FastAPI | 原生异步 + Pydantic 校验 + 免费 Swagger；同步推理要用线程池隔离 |
| SQLAlchemy | ORM 一套代码兼容 SQLite/MySQL；引擎参数因库而异 |
| YOLOv8 | 一阶段 anchor-free 检测器（C2f + 解耦头 + CIoU/DFL），实时 + 可定位 |
| OpenCV | numpy/BGR 世界的拉流、读写、画框 |
| MediaMTX | 浏览器不能播 RTSP → 转 FLV/WebRTC |
| Vue3 + Element Plus | 中文中后台的最优组合；Vite 代理解决跨域 |
| reportlab / openpyxl | 报表导出；各有中文与图片的坑（第 9 篇） |
