# 第 2 篇：项目经理怎么把一句话需求拆成可验收的需求文档

> 系列博客第 2 篇。这一篇没有代码，但比代码更重要——因为**没有需求文档，代码就是空中楼阁**。我从项目经理的角度，完整演示一遍"一句话需求 → 需求规格说明书"的全过程，用的就是本项目的真实需求。

---

## 开头：一个真实的"一句话需求"

某建筑施工企业信息化部，接到分管安全的副经理一句话：

> "市里推智慧工地，安全帽、马甲这些智能识别要搞起来。你调研一下，出个方案。"

就这一句话，背后全是坑：

- "智能识别"识别什么？安全帽？马甲？口罩？抽烟？**范围不定**；
- 识别到之后干什么？报警？留痕？统计？导出报告？**价值不定**；
- 用谁的摄像头？现有的海康大华能用吗？**接口不定**；
- 谁来用？安全员？项目经理？总部？**用户不定**；
- 部署在哪？项目部电脑还是公司机房？**环境不定**；
- 预算多少？工期多久？怎么验收？**约束不定**。

需求分析的全部工作，就是把这一句话变成一份**能指导开发、能验收、能定价**的《需求规格说明书》。本系列的这个项目，就是按下面这套流程做出来的。

## 1. 需求分析五步法

```
① 识别干系人与目标 → 谁要什么？为什么？
② 梳理业务场景     → 系统在什么流程中被使用？
③ 提取功能需求     → 系统要"做什么"（FR 编号）
④ 定义非功能需求   → 系统要"做到什么程度"
⑤ 确定验收标准     → 怎么证明做完了、做好了
```

### ① 干系人分析：五个角色，五种诉求

| 干系人 | 核心诉求 | 对系统的意义 |
|---|---|---|
| 企业安全总监 | 降事故率、满足监管、有据可查 | 驱动"自动抓拍留痕"和"PDF 周报月报" |
| 工地安全员 | 每天看现场违规、及时制止 | 驱动"实时监控 + 预警" |
| 项目经理（我方） | 快速部署、低维护、演示效果好 | 驱动"本地一键启动 + 演示模式" |
| 总部管理层 | 汇总多项目数据做决策 | 驱动"数据看板 + 点位排行 + 周报/月报" |
| 监管部门 | 有合规证据 | 驱动"证据图 + 日志导出" |

> 💡 **需求不是"用户要什么"的清单，而是"各干系人诉求的平衡"**。本项目最终很多设计——比如"临时演示模式"、"本地 SQLite 零依赖"——就是平衡了"安全员要实用"和"项目经理要好部署"两类诉求的结果。

### ② 业务场景：用"用户故事"把场景固定下来

用户故事的标准格式：**作为<角色>，我希望<能力>，以便<价值>**。

本项目的核心用户故事（10 条，每条都能在仓库里找到对应功能）：

| 编号 | 用户故事 | 对应功能（可验证） |
|---|---|---|
| US-01 | 作为安全员，我希望摄像头自动识别违规穿戴，以便及时制止 | YOLOv8 检测 + direct 判定 |
| US-02 | 作为安全员，我希望违规瞬间自动拍照留证据，以便处理有据可查 | 原始帧 + 标注证据图双份入库 |
| US-03 | 作为值班人员，我希望浏览器里实时看到摄像头画面，以便远程巡查 | MediaMTX + flv.js |
| US-04 | 作为安全员，我希望同一违规不要反复刷屏，以便不被骚扰 | `dedup_seconds` 去重 |
| US-05 | 作为管理者，我希望看到违规趋势和分布，以便针对性整改 | 看板 7/30/90 天趋势、类型分布、点位排行 |
| US-06 | 作为管理者，我希望每周/每月自动得到安全报告，以便向公司汇报 | PDF 周报/月报 |
| US-07 | 作为安全员，我希望违规频发时系统主动提醒，以便不用翻数据 | 预警规则 + 顶栏铃铛 |
| US-08 | 作为演示工程师，我希望不接监控也能演示，以便客户现场验收 | 临时演示模式 |
| US-09 | 作为操作员，我希望违规记录能导出 Excel 给别人看，以便信息共享 | Excel 导出（含图片） |
| US-10 | 作为项目经理，我希望系统装起来简单，以便快速交付 | SQLite 零依赖 + Docker + start-local.bat |

### ③ 功能需求：编号化、可测试

功能需求必须**可测试**——每一条都能写出验收动作。本项目的功能需求分成 7 个模块（编号 FR-A~G），这里给完整清单，这也是后面所有技术篇的"需求地图"：

**模块 A：摄像头管理**（`routers/cameras.py` + `views/camera/`）

| 编号 | 需求 |
|---|---|
| FR-A1 | 录入摄像头：名称、安装点位、RTSP 地址、启用状态 |
| FR-A2 | 启用/停用摄像头（推理服务只拉取启用中的） |
| FR-A3 | 显示在线/离线状态（推理服务心跳上报） |
| FR-A4 | RTSP 连通性测试（8 秒兜底，不阻塞事件循环） |

**模块 B：AI 识别与抓拍**（`inference/` + `routers/violations.py`）

| 编号 | 需求 |
|---|---|
| FR-B1 | 基于 ppe.pt（10 类）识别 10 种目标 |
| FR-B2 | direct 判定：出现 NO-* 即违规（no_helmet / no_vest / no_mask） |
| FR-B3 | 违规自动抓拍：原始帧 + 标注证据图双份 |
| FR-B4 | 同一摄像头同一类型 30 秒内不重复上报 |
| FR-B5 | 置信度阈值可覆盖（前端"灵敏度"滑块） |
| FR-B6 | 违规入库：摄像头、类型、置信度、图片、检测明细 JSON、时间 |
| FR-B7 | `no_save=true` 只检测不入库（监控页 AI 叠加复用） |

**模块 C：违规记录与安全日志**（`views/violation/`、`views/log/`）

| 编号 | 需求 |
|---|---|
| FR-C1 | 列表筛选（类型/摄像头/日期）+ 分页 + 详情抽屉（原图/标注图切换 + 检测明细） |
| FR-C2 | Excel 导出：筛选一致、内嵌图片缩略图、中文文件名 |
| FR-C3 | 导出行数上限 5000，防内存失控 |

**模块 D：数据看板**（`Dashboard.vue` + `/api/logs/dashboard`）

| 编号 | 需求 |
|---|---|
| FR-D1 | 总违规数、今日违规数、在线摄像头数 |
| FR-D2 | 趋势图 7/30/90 天切换，按天补零 |
| FR-D3 | 违规类型分布 |
| FR-D4 | 摄像头排行 + 点位排行（location，未填归"未填点位"） |
| FR-D5 | 15 秒自动刷新，新增违规弹提醒 |

**模块 E：预警中心**（`routers/warnings.py` + `views/warning/`）

| 编号 | 需求 |
|---|---|
| FR-E1 | 规则 CRUD：摄像头（空=全部）、类型（空=全部）、窗口分钟、次数阈值、启用 |
| FR-E2 | 违规入库自动检查：窗口内违规数 ≥ 阈值 → 生成预警事件 |
| FR-E3 | 同摄像头+同类型 10 分钟冷却防刷屏 |
| FR-E4 | 事件分页、未读筛选、标记已读、全部已读 |
| FR-E5 | 顶栏铃铛：未读徽标 + 10 秒轮询 + 弹窗 |

**模块 F：报表导出**（`logs.py` 的 `/report`）

| 编号 | 需求 |
|---|---|
| FR-F1 | PDF 周报（week）/ 月报（month） |
| FR-F2 | 内容：统计摘要 + 趋势图 + 类型分布 + 点位排行 + 前 50 条明细 |
| FR-F3 | 中文正常（reportlab 内置 STSong-Light，无需系统字体） |

**模块 G：认证与演示**

| 编号 | 需求 |
|---|---|
| FR-G1 | JWT 登录（admin/admin123），401 跳登录页 |
| FR-G2 | 环境自检 `/api/demo/status` |
| FR-G3 | 演示链路违规入库（camera_id=0，名称"临时演示"） |

### ④ 非功能需求：做到什么程度

功能需求回答"做什么"，非功能需求回答"做到什么程度"。**这部分的量化指标是项目经理与客户谈判的重点**：

| 类别 | 要求 | 实现证据 |
|---|---|---|
| 性能 | 多路摄像头并发检测不互相阻塞 | 每摄像头一个线程（`inference/main.py`） |
| 性能 | 演示接口不阻塞事件循环 | `run_in_threadpool`（`demo.py`） |
| 性能 | 首次演示请求不卡顿 | 启动预热线程 + 前端超时 60s |
| 可用性 | 摄像头断流自愈 | 断流重连 + 心跳离线上报 |
| 可用性 | 预警不刷屏 | 10 分钟冷却 + 去重 |
| 可维护性 | 检测/判定/标注双份同步 | CLAUDE.md 约定 + 注释声明 |
| 可移植性 | 本地零依赖（SQLite）/ Docker（MySQL） | `DATABASE_URL` 环境变量切换 |
| 可靠性 | 时间戳口径统一（防 UTC 差 8 小时） | Python 侧 `datetime.now()` 写入 |
| 易用性 | 演示环境可自检，避免现场翻车 | `/api/demo/status` + 一键自检 |

### ⑤ 验收标准：怎么证明"做完了"

每个 FR 配验收动作。示例（完整验收矩阵可以做成验收表）：

| 需求 | 验收动作 | 预期结果 |
|---|---|---|
| FR-B1 | 对含未戴安全帽工人的测试图运行检测 | 输出 NO-Hardhat 框且置信度 ≥ 0.5 |
| FR-B3 | 触发一次违规 | violations 表新增记录，image_url 与 anno_url 两文件均存在 |
| FR-B4 | 同一画面持续 60 秒 | 30 秒内仅 1~2 条记录 |
| FR-D2 | 看板切换 7/30/90 天 | 日期轴覆盖对应窗口，无数据日期显示 0 |
| FR-E2 | 建规则"60 分钟 ≥ 3 次"，手动产生 3 条违规 | 生成 1 条预警事件，铃铛未读 +1 |
| FR-F1 | 点击导出月报 | 下载 `安全月报_2026-10-01_2026-10-31.pdf`，中文无乱码 |

## 2. 需求文档的常见错误（评审时高频扣分点）

1. **需求与场景脱节**：只写"系统要有识别功能"，不写谁在什么时候用。→ 用用户故事强制写场景；
2. **需求不可测试**："识别准确率要高"——多高？→ 改为"置信度 ≥ 0.5 时正确输出违规类"；
3. **功能与非功能混淆**："页面要美观"是非功能需求（可用性），却常被写进功能列表；
4. **没有验收标准**：开发完不知道什么叫"做完"。→ 每个 FR 至少一条验收动作；
5. **范围蔓延**：把"人脸识别考勤""抽烟检测"全塞进来。→ 用 P0/P1/P2 优先级控制范围（第 3 篇）。

## 总结

- 需求五步法：干系人 → 场景 → 功能需求 → 非功能需求 → 验收标准；
- 用户故事格式 `作为…我希望…以便…` 是把模糊诉求变成明确需求的最佳工具；
- 好的需求文档 = **可测试的 FR + 有量化指标的 NFR + 可执行的验收动作**；
- 需求要有编号、有映射——拿到需求文档就能在代码里找到对应模块，这叫"需求可追溯"。
