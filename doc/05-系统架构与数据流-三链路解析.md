# 第 5 篇：三条业务链路——架构总览与"双份同步"约定

> 系列博客第 5 篇。上一篇讲"选什么技术"，这一篇讲"怎么把它们组织成一个系统"：整体架构、三条业务链路的数据流、以及本仓库最核心的维护约定——检测/判定/标注代码**双份同步**。

## 开头：系统不是"代码的堆砌"

技术选型完了，如果只是把 FastAPI、YOLO、Vue3 的代码堆在一起，那叫"demo"，不叫"系统"。

系统要有：明确的模块边界、清晰的数据流、稳定的约定。这一篇，我们看这套系统的骨架。

## 2. 链路一：正式链路（RTSP 摄像头 → 后端入库）

### 数据流

```
海康/大华等摄像头(RTSP:554)
  → MediaMTX 转发（8554 收，8080 出，供前端预览 + 稳定拉流）
  → 推理服务 StreamWorker（OpenCV 拉流，每摄像头一个线程）
  → 每 N 帧检测一次（infer_every_n_frames=5）
  → judge_violations 判定（direct 模式）
  → 命中违规 → 去重(dedup_seconds=30) → 抓拍原始帧+标注图
  → POST /api/violations/with-image（multipart：file+anno+元数据+detections JSON）
  → FastAPI 入库（violations 表）→ 触发预警检查
  → Vue3 后台展示 / 导出
```

### 入口：inference/main.py

```python
def fetch_cameras(config: dict) -> list:
    """从后端获取启用中的摄像头"""
    cams = requests.get(f"{config['backend_url']}/api/cameras", timeout=10).json()
    return [c for c in cams if c.get("enabled", True)]   # 只拉启用中的

def main():
    cameras = fetch_cameras(config)
    ...
    for cam in cameras:
        w = StreamWorker(cam, config)
        t = threading.Thread(target=w.run, daemon=True, name=f"worker-cam{cam['id']}")
        t.start()   # 每摄像头一个线程，互不阻塞
```

**为什么每摄像头一个线程？** 一路摄像头断流/卡顿不能影响其他路。Python 的 `threading` 在这里很合适——因为瓶颈是 IO（拉流、网络请求）和 GPU/CPU 推理，用线程足够。

### 核心循环：stream_worker.py

```python
def run(self):
    while self._running:
        if cap is None or not cap.isOpened():
            cap = cv2.VideoCapture(self.camera["rtsp_url"])   # 拉流
            ...
        ret, frame = cap.read()
        if not ret:                       # 断流
            cap.release(); cap = None; self._heartbeat(False)
            continue
        self._heartbeat(True)             # 心跳：在线
        frame_idx += 1
        if frame_idx % self.infer_every != 0:
            continue                      # 每5帧检测一次（省CPU）
        detections = self.detector.predict(frame)
        violations = judge_violations(detections, self.rule, mode=self.judge_mode)
        for vio in violations:
            self._report(vio, frame, conf, detections)   # 抓拍+上报
```

**三个关键设计**：

1. **每 N 帧检测一次**：30fps 的流实际检测 6 次/秒，CPU 压力大降。工程上"检测频率 ≠ 帧率"是常态；
2. **心跳**：`POST /api/cameras/{id}/status` 让后台显示在线/离线——这是"摄像头状态"的底层来源；
3. **断流自愈**：`cap.read()` 失败就 `release()` 重连，同时上报离线。

### 上报：去重 + 双图

```python
def _report(self, vio_type, image_np, confidence, detections):
    now = time.time()
    if now - self._last_report.get(vio_type, 0) < self.dedup_seconds:
        return                                    # 30秒内同类型不重复
    self._last_report[vio_type] = now

    # 原始帧 + 标注证据图双份保存
    cv2.imwrite(local_path, image_np)
    anno_image = draw_annotations(image_np, detections or [], [vio_type])
    cv2.imwrite(anno_local, anno_image)

    # multipart 上报（file + anno 两张图）
    requests.post(f"{self.backend_url}/api/violations/with-image",
        files={"file": (...), "anno": (...), },
        data={"camera_id":..., "camera_name":..., "violation_type":...,
              "confidence":..., "detections": json.dumps(...)}, timeout=10)
```

**去重（dedup）的底层原因**：违规是持续的（有人一直没戴帽），如果不去重，30 秒能上报几百条相同违规——数据库爆炸、台账被刷屏。`dedup_seconds` 让同一摄像头同一类型 30 秒内只报一次。

## 3. 链路二：临时演示链路（笔记本摄像头，零设备依赖）

### 为什么需要它？

正式链路需要三样：RTSP 摄像头 + MediaMTX + 推理服务。客户现场演示时**一样都没有**。演示链路的答案：浏览器直接取笔记本摄像头帧，后端直接推理。

### 数据流

```
笔记本摄像头（浏览器 getUserMedia）
  → 前端每 500ms 截一帧（canvas → JPEG）
  → POST /api/demo/detect（multipart 图片 + conf 灵敏度 + no_save 标志）
  → 后端 get_detector() 懒加载单例（启动时已预热）
  → run_in_threadpool(detector.predict, img)
  → judge_violations 判定（与正式链路同一份 judge.py 逻辑）
  → 违规时：保存原始帧+标注图 → 入库（camera_id=0, "临时演示"）
  → 返回检测框/违规列表 → 前端 canvas 叠加绘制
```

### 三个关键设计（demo.py）

**① 懒加载单例 + 双重检查锁**（避免并发首请求重复加载模型）：

```python
_detector: YoloDetector | None = None
_detector_lock = threading.Lock()

def get_detector() -> YoloDetector:
    global _detector
    if _detector is None:
        with _detector_lock:
            if _detector is None:      # 双重检查锁（DCL）
                _detector = YoloDetector(model_path=_find_model_path(), ...)
    return _detector
```

**为什么双重检查？** 两个并发请求同时到达时，如果没有锁，会加载两次模型（浪费内存和时间）。DCL 保证：即使同时进来了，也只有一个线程真正创建实例。

**② 模型路径自动搜索**（覆盖 Docker 与本地两种启动场景）：

```python
candidates = [settings.DEMO_MODEL_PATH, "weights/ppe/ppe.pt",
    "../weights/ppe/ppe.pt", "weights/ppe.pt"]
```

**③ 线程池推理**（不阻塞事件循环）+ **no_save 复用**：实时监控页的 AI 叠加也调本接口（`no_save=true` 只检测不入库）。

## 4. 链路三：原始脚本（视频文件 PPE 检测）

| 脚本 | 用途 | 启动命令 |
|---|---|---|
| `Safety-Detection.py` | 实时窗口播放检测 | `uv run python Safety-Detection.py` |
| `Safety-Detection-export.py` | 导出标注视频（CPU） | `uv run python Safety-Detection-export.py --input videos/x.mp4 --output videos/x_out.mp4` |
| `Safety-Detection-export-gpu.py` | GPU 加速导出 | `uv run python Safety-Detection-export-gpu.py --input videos/x.mp4 --output videos/x_out.mp4 --half` |

标注配色约定（与系统一致）：**红色 = 违规（NO-*），绿色 = 合规装备，蓝色 = 其他目标**。

这条链路的价值：① 开发调试模型的实验台（不用接摄像头）；② 教学演示；③ 脚本内硬编码 `classNames` 列表（换模型时也要同步改）。

## 5. 核心约定：检测/判定/标注代码"双份同步"

### 5.1 为什么会有双份？

推理服务（`inference/`）和后端演示模式（`backend/app/detection/`）**各自独立加载模型**（推理服务是独立进程，后端演示直接加载），但必须复用同一套检测/判定/标注逻辑——否则两条链路识别结果不一致，客户演示与正式部署结果对不上。

所以 CLAUDE.md 规定：

> 以下文件在 `inference/` 与 `backend/app/detection/` 之间**逐行一致**，修改任意一处必须同步另一处：
> - `detector.py`（YOLO 封装）
> - `judge.py`（违规判定）
> - `annotate.py`（抓拍标注）

### 5.2 代码里的"同步声明"

```python
# backend/app/detection/judge.py
"""违规判定（与 inference/judge.py 保持一致）：支持两种模式 ..."""

# backend/app/detection/annotate.py
"""违规抓拍标注（与 inference/annotate.py 双份同步，修改必须同步两处）..."""

# backend/app/detection/detector.py
"""YOLO 检测器封装（与 inference/detector.py 保持一致）"""
```

### 5.3 违反的后果

| 违反场景 | 表现 |
|---|---|
| 只改了 inference/judge.py | 正式链路新逻辑、演示链路旧逻辑 → 同一帧两种结果 |
| 只改了 annotate.py 配色 | 两条链路证据图颜色不一致 → 台账混乱 |

> 💡 为什么不用"抽公共包"一劳永逸？——可以（第 11 篇扩展方向提过），但当前架构下"推理服务独立进程"与"后端演示模式"解耦，抽公共包需要额外工程投入。**注释约定 + 文档约定是务实的选择**，代价是"改一处必须想起另一处"。

## 6. 部署形态：本地 vs Docker

| 维度 | 本地开发（SQLite） | Docker 部署（MySQL） |
|---|---|---|
| 启动 | `start-local.bat`（后端+前端） | `docker compose up -d --build` |
| 数据库 | SQLite（自动建表） | MySQL 8.0（init.sql 初始化） |
| 图片存储 | `backend/images/` | 共享 volume `/data/images` |
| 推理服务 | 手动 `CONFIG_PATH=inference/config.local.yaml uv run python -m inference.main` | 容器自动启动 |
| 模型路径 | 自动搜索 | 挂载 `/app/weights` |
| 访问 | http://localhost:3000（Vite 代理） | http://localhost（nginx 反代） |

> ⚠️ 重要陷阱：推理服务 **cwd 必须是仓库根目录**（`inference` 是包名，非顶层目录），否则 `python -m inference.main` 与相对路径配置失效。

## 总结

- **五模块**：backend（大脑）、inference（眼睛）、frontend（脸）、deploy（血管）、原始脚本（实验台）；
- **三条链路**：正式（RTSP+推理服务）、演示（笔记本摄像头+后端推理）、脚本（视频文件）；
- **关键机制**：每摄像头一线程、每 N 帧检测、去重、心跳、线程池推理、懒加载单例、路径自动搜索；
- **双份同步**：detector/judge/annotate 三文件逐行一致，改一处必须改另一处；
- **部署双形态**：本地 SQLite 零依赖 vs Docker 五容器编排。
