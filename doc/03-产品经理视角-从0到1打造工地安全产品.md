# 第 3 篇：从立项到验收——项目管理与产品设计实录

> 系列博客第 3 篇。上一篇讲了"需求文档怎么写"，这一篇讲**项目管理**：拿到需求之后，项目怎么排计划、怎么控风险、怎么定价、怎么验收。同时从产品经理视角讲清楚本项目的 `优化报告.md` 是怎么做出来的（P0/P1/P2 优先级、演示动线、四阶段路线图）。

---

## 开头：项目经理的一天

想象你就是这个项目的项目经理。客户一句话需求（第 2 篇），需求文档出来了，然后呢？

你要回答一堆问题：**几个人干？干多久？多少钱？风险在哪？哪天验收？验收标准是什么？** 如果这些没想清楚，项目就是"做不完、验不了、收不到钱"的灾难。

这一篇，我用本项目的真实决策过程，把项目管理的关键动作过一遍。

## 1. 项目管理第一步：WBS（工作分解结构）

WBS = Work Breakdown Structure，把项目拆成可交付的工作包。**拆到"能估算工作量"的粒度为止**。本项目的 WBS 顶层如下：

```
工地AI安全监测系统
├── 1 需求与方案（0.5 天）
│   ├── 1.1 干系人访谈、现场调研
│   ├── 1.2 需求规格说明书
│   └── 1.3 技术选型评审
├── 2 系统搭建（2~3 天）
│   ├── 2.1 后端脚手架（FastAPI + SQLAlchemy + JWT）
│   ├── 2.2 推理服务（YOLO 检测 + 判定 + 抓拍 + 上报）
│   ├── 2.3 前端框架（Vue3 + 路由 + 登录 + 布局）
│   └── 2.4 数据模型与建表
├── 3 产品优化（5~7 天，分三个阶段）
│   ├── 3.1 阶段一"先救场"（P0 演示项）
│   ├── 3.2 阶段二"补齐正式功能"（P1）
│   └── 3.3 阶段三"打磨演示体验"（P2）
├── 4 数据驱动（按需）
│   ├── 4.1 看板聚合 + 点位统计
│   ├── 4.2 PDF 周报/月报
│   └── 4.3 预警中心
├── 5 部署与交付（1~2 天）
│   ├── 5.1 本地一键启动（start-local.bat）
│   ├── 5.2 Docker Compose 编排
│   └── 5.3 客户现场验收
└── 6 文档（贯穿全程）
    ├── 6.1 README / CLAUDE.md / 优化报告
    └── 6.2 用户手册 / 培训
```

**WBS 的价值**：让"项目"从一句话变成一张可估算、可排期、可追责的清单。每个工作包都有交付物。

## 2. 里程碑与路线图：分阶段交付

项目管理里有个原则：**不要憋一个大版本最后一次性交付**，要分阶段、每阶段都可验证。本项目的四阶段路线图（仓库里 `优化报告.md` §6 原文）：

| 阶段 | 名称 | 内容 | 时长 | 里程碑验收 |
|---|---|---|---|---|
| 阶段一 | 先救场 | P0-1 标注证据图、P0-2 监控开箱即用+AI叠加、P0-3 演示加载提示 | 1~2 天 | 客户现场演示不翻车 |
| 阶段二 | 补齐正式功能 | P1-1~P1-6（看板图表、详情抽屉、测试连接、实时提醒、筛选分页、导出带图） | 2~3 天 | 后台每天用起来 |
| 阶段三 | 打磨演示体验 | P0-4 多路同屏 + P2 系列 | 1~2 天 | 演示更有"产品感" |
| 阶段四 | 数据驱动 | 周报/月报、点位统计、PDF 报告、预警中心 | 按需 | 数据能讲管理故事 |

**为什么这样排？** 顺序的逻辑是：**先救最疼的 → 再补最常用的 → 再打磨体验 → 最后做长期数据能力**。每一步都可交付、可演示、可止损。如果客户中途变卦或砍预算，前三阶段的成果已经是"能用的产品"。

## 3. 风险管理：把"会翻车的事"列出来

项目经理最重要的能力之一：**预判风险并提前处置**。本项目的真实风险清单（很多是踩过坑才总结的）：

| 风险 | 概率 | 影响 | 处置措施（真实做法） |
|---|---|---|---|
| 模型加载慢，演示像"卡死" | 高 | 高 | 启动预热模型 + 前端全屏"加载中"提示 + 超时放宽 60s |
| 浏览器不能播 RTSP | 高 | 高 | MediaMTX 转 FLV + flv.js |
| SQLite 时间戳 UTC 差 8 小时 | 中 | 高 | 统一 Python 本地时间写入 + 存量迁移（第 9 篇详述） |
| 第三方库升级破坏 API（reportlab） | 中 | 高 | 锁版本 + 手绘图表兜底（第 9 篇详述） |
| 检测/判定代码双份不同步 | 高 | 中 | CLAUDE.md 约定 + 文件头注释 + 验收核对清单 |
| 演示现场摄像头权限被拦 | 中 | 高 | 环境自检接口 + 前端引导 + 只要求 localhost/https |
| 客户摄像头 RTSP 填错 | 高 | 中 | 摄像头"测试连接"按钮（P1-3） |
| 违规上报刷屏 | 中 | 中 | dedup 去重 + 预警 10 分钟冷却 |

> 💡 项目管理的核心不是"消灭风险"，而是"**把高风险项前置**"——先做容易翻车、影响大的事。看阶段一的内容，全部是"演示翻车"类风险。

## 4. 优先级方法论：P0 / P1 / P2（产品经理视角）

这是 `优化报告.md` 的核心。判断标准写得很直白：

> **客户在现场 10 秒内能感知的 > 后台日常使用便利性 > 长期数据能力**

| 级别 | 定义 | 判定标准 |
|---|---|---|
| **P0** | 演示关键路径 / 客户一眼看到的"AI 感" | 不做 → 演示翻车或产品"没 AI 感" |
| **P1** | 核心功能完善（后台管理员每天用） | 不做 → 日常使用不便、台账不专业 |
| **P2** | 体验打磨（锦上添花） | 不做 → 不致命，但做了更有"产品感" |

对照本仓库（`优化报告.md` §4）：

- **P0 四项**：标注证据图、监控开箱即用+AI 叠加、演示启动反馈+流畅度、多路同屏；
- **P1 六项**：看板图表化、违规详情抽屉、摄像头测试连接、违规实时提醒、筛选补全+分页、导出增强；
- **P2 八项**：演示统计面板、违规时间线、全屏演示、可调节项、状态自动刷新、环境自检、反馈细节、登录体验。

### 4.1 排期工具：客户价值 × 工作量矩阵

```
         客户价值
  高 │  P0-1 标注证据图      │  P1-1 看板图表化
     │  P0-2 监控AI叠加      │  P1-2 违规详情抽屉
     │  P0-3 演示加载提示    │  P1-4 违规实时提醒
     │  (价值高、工作量小)   │  (价值高、工作量中)
     ├─────────────────────┼─────────────────────
     │  P2 系列             │  (价值中、工作量大的
     │  全屏/统计/引导等     │   长期数据能力)
  低 │  (有空就做)          │  (按需、阶段四)
         小                 大  → 工作量
```

**排期口诀**：先做"价值高、工作量小"（左上象限），再做"价值高、工作量中"，最后有空做"锦上添花"。

## 5. 演示动线设计：客户 10 秒内被打动

产品经理有个方法论叫**动线设计**：把客户体验流程当成"剧本"，每一步都要顺畅、有亮点。本项目的演示动线（`优化报告.md` §1）：

```
登录 → 临时演示（笔记本摄像头）→ 违规抓拍留痕 → 数据看板 → 实时监控 → 安全日志导出
```

| 动线环节 | 优化前的问题 | 优化后 |
|---|---|---|
| 登录 | 密码输错没提示 | P2-8：记住密码 + 失败原因提示 |
| 临时演示 | 首次加载 10~30s 无提示，像卡死 | P0-3：全屏"加载中"提示 + FPS/耗时显示 |
| 违规抓拍 | 只有裸图，看不出 AI 标了什么 | P0-1：标注证据图（检测框 + 中文横幅） |
| 数据看板 | 只有总数和一张表 | P1-1：趋势图 + 类型分布 + 排行 |
| 实时监控 | 单路、无 AI 叠加、地址写死 | P0-2 / P0-4：多路同屏 + AI 叠加 |
| 安全日志 | 导出无图、无筛选 | P1-6：Excel 内嵌违规图片 |

> 💡 产品经理视角的关键：**客户信的不是算法指标，而是一条完整、可解释的"证据链"**——检测出违规 → 抓拍标注图（证据）→ 入库台账（留痕）→ 导出报告（汇报）。这就是为什么 P0-1（标注证据图）排最高优先。

## 6. 一个 P0 需求从报告到代码的完整旅程

以 P0-1 为例，看需求怎么落地：

**报告描述**（为什么）：
> 现状：入库的都是原始帧裸图，客户看不到"AI 框出的违规点"。优化：抓拍时绘制检测框 + 违规标签水印。

**技术设计**（怎么做）：
- 新增 `backend/app/detection/annotate.py`（与 `inference/annotate.py` 逐行同步）；
- `draw_annotations()` 画检测框（违规红/合规绿/其他蓝）+ 中文横幅；
- `violations` 表新增 `anno_url`、`detections_json` 列，`_ensure_schema()` 启动自动补列。

**代码落点**（`annotate.py`）：

```python
NEGATIVE_CLASSES = {"NO-Hardhat", "NO-Mask", "NO-Safety Vest"}
POSITIVE_CLASSES = {"Hardhat", "Mask", "Safety Vest"}

def draw_annotations(image, detections, violations):
    img = image.copy()
    if violations:
        labels = [VIOLATION_LABELS.get(v, v) for v in violations]
        img = _draw_banner(img, "违规: " + "、".join(labels))
    for d in detections:
        color = BLUE
        if d.cls_name in NEGATIVE_CLASSES: color = RED
        elif d.cls_name in POSITIVE_CLASSES: color = GREEN
        cv2.rectangle(img, ...)   # 检测框
    return img
```

**验收验证**：真实视频帧检出违规并出标注图（含红色横幅像素）；双图 + 检测明细成功入库。

> 💡 一个完整需求 = 报告描述（为什么）→ 技术设计（怎么做）→ 代码落点（文件）→ 验收验证（证据）。`优化报告.md` §4.1 的"实施完成对照表"就是这种闭环的文档化。

## 7. 成本与验收：怎么定价、怎么算"做完"

### 7.1 估算逻辑（给客户报价时用）

```
总工作量 ≈ Σ(每个 WBS 工作包的人天) × 单价
```

按本项目的 WBS：搭建约 3 人天 + 产品优化 5~7 人天 + 部署交付 1~2 人天 + 文档贯穿 = **约 10~12 人天**。单人 + AI 辅助实际压缩到一半左右（第 10 篇讲 AI 如何提速）。

> 💡 **报价策略**：分阶段报价比打包报价更稳——阶段一、二、三的成果随时可交付，客户每阶段都能看到价值，尾款好收。

### 7.2 验收流程

```
① 需求文档评审（双方确认 FR/NFR）
② 阶段里程碑验收（每阶段演示 + 对照 FR 清单打勾）
③ 试运行（接真实摄像头跑 3~7 天）
④ 正式验收（验收矩阵全项通过 + 交付文档）
```

验收矩阵示例（对应第 2 篇 FR）：

| 需求 | 验收动作 | 预期结果 |
|---|---|---|
| FR-B3 | 触发一次违规 | violations 新增记录，image_url 与 anno_url 两文件均存在 |
| FR-E2 | 建规则"60分钟≥3次"，手动产生 3 条违规 | 生成 1 条预警事件，铃铛未读 +1 |
| FR-F1 | 导出月报 | 下载 `安全月报_*.pdf`，中文无乱码 |

## 8. 管理文档沉淀：CLAUDE.md 和优化报告

项目经理做完一个项目，最有价值的产出之一就是**把经验沉淀成文档**。本仓库有两份关键管理文档：

| 文档 | 作用 | 核心内容 |
|---|---|---|
| `CLAUDE.md` | 项目"宪法"：约定与陷阱，AI 与人的共同记忆 | 架构、双份同步规则、SQLite 陷阱、常用命令、新接口清单 |
| `优化报告.md` | 产品迭代路线图 | 用户画像、演示动线评估、P0/P1/P2 清单、价值×工作量矩阵、四阶段路线图、实施完成对照表 |

**为什么 AI 时代文档更重要？** 因为 AI 每次会话都会先读 CLAUDE.md——把踩过的坑写进文档，等于给 AI"接种疫苗"，它就不会再犯同样的错误（第 10 篇详述）。

## 总结

- **WBS**：把项目拆到可估算粒度，是排期、定价、追责的基础；
- **分阶段交付**：每阶段可验证、可止损，不憋大招；
- **风险管理**：把高风险项前置（演示翻车类 > 后台便利类 > 长期数据类）；
- **优先级**：P0/P1/P2 + 价值×工作量矩阵，是排期标准工具；
- **演示动线**：客户 10 秒被打动，靠的是完整"证据链"；
- **文档沉淀**：CLAUDE.md 是项目宪法，优化报告是迭代路线图。
